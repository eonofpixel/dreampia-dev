# Spike: @sigstore/verify in Electron 33 main process

**Status**: GO
**Date**: 2026-05-09
**Spike for**: v2.3.0 Plugin GA — US-200 (Phase 2 HARD GATE before US-201/202/203)
**Decision authority**: codex architect review (G2 tightening: identity policy mandatory)
**Plan reference**: `.omc/plans/v2.3.0-plugin-ga.md` §4 Phase 2.1

---

## Question

Does `@sigstore/verify` work in Electron 33 main process within the v2.3.0 bundle-size and offline-policy constraints?

## Findings

### 1. Bundle size (well within ≤5 MB budget)

| Measurement | Value |
|-------------|-------|
| `node_modules/@sigstore/` total (4 sub-packages: bundle / core / protobuf-specs / verify) | **848 KB** |
| Direct dep added to `package.json` | `@sigstore/verify@^3.1.0` |
| Sub-packages pulled transitively | `@sigstore/bundle`, `@sigstore/core`, `@sigstore/protobuf-specs` |
| Headroom vs G2 codex 5 MB budget | **~6× under budget** |

`scripts/check-dist-size.cjs` is now in place to enforce ≤5 MB delta against a checked-in baseline (run `--update` after a release ships).

### 2. Module exports (sufficient API for v2.3.0 needs)

```js
> Object.keys(require('@sigstore/verify'))
[ 'toSignedEntity', 'PolicyError', 'VerificationError', 'toTrustMaterial', 'Verifier' ]
```

Mapping to v2.3.0 requirements:

| v2.3.0 need (G2 codex tightening) | sigstore API |
|------------------------------------|--------------|
| Verify Sigstore bundle against trust root | `Verifier.verify(signedEntity, policy)` |
| Identity policy: pin `iss` URL match | `Verifier` policy `certificateIdentities[].issuer` |
| Identity policy: pin `sub` glob match | `Verifier` policy `certificateIdentities[].subjectAlternativeName` (glob via `regexp` field) |
| Surface verification failures distinctly | `VerificationError` (signature) vs `PolicyError` (identity-mismatch) — exactly what `ManifestVerificationResult` discriminates on |
| Convert raw bundle to verifiable entity | `toSignedEntity(bundle, artifact)` |
| Trust root construction | `toTrustMaterial(tufRoot, options)` |

The four-way `ManifestVerificationResult` union we landed in US-101 maps cleanly:
- `verified` → no error thrown by `Verifier.verify`
- `identity_mismatch` → `PolicyError`
- `signature_invalid` → `VerificationError`
- `unsigned` → caller decides (no bundle attached → skip Verifier call entirely)

### 3. Electron 33 main-process compat

Smoke test: `node -e "require('@sigstore/verify')"` succeeded under the project's installed Node (Node 20.x via Electron 33). All sub-packages are pure JS / CJS — no native bindings, no preload tricks. The library will load identically inside Electron's Node-runtime main process.

**Renderer**: explicitly NOT supported. The library expects Node `Buffer`, `crypto`, and timing-sensitive primitives that pollute the trust boundary if exposed via preload. AC-6.4 already mandates main-process-only.

### 4. Offline support (G2 + codex air-gap policy)

Sigstore's verify model:
- **Trust root** must be present locally (TUF-rooted JSON describing Fulcio + Rekor pubkeys). Library does NOT fetch root at verify time if `toTrustMaterial` is supplied with bundled content.
- **Signed entity** is the manifest + Sigstore bundle. The Sigstore bundle (`*.sigstore`) carries the cert chain, signature, and inclusion proof inline.
- **Rekor inclusion proof** is verified offline if the bundle includes the transparency-log entry (it should — `gh attestation` produces such bundles by default since 2024).

→ **Offline strict-mode install is feasible** with no network calls: `sigstoreRoot.json` (US-202) bundled at build, `*.sigstore` bundle attached to GitHub Release artifact, `Verifier.verify(...)` runs purely in-process.

→ **TUF root refresh** must happen via electron-updater channel only (no runtime fetch from `tuf.sigstore.dev`). `release-checklist.md` warning when `now - lastTufRefresh > 6mo` (AC-6.7).

### 5. Identity policy claim API

The `Verifier` policy interface accepts:

```ts
{
  certificateIdentities: [{
    issuer: 'https://token.actions.githubusercontent.com',
    subjectAlternativeName: {
      type: 'URI',
      regexp: 'repo:eonofpixel/sample-plugin:ref:refs/tags/v.*',
    },
  }],
}
```

This is the **wire format** for the `signing.identity.{issuer, subject_pattern}` we already defined on `McpManifestSchema` (US-101). `manifestVerify.ts` (US-201) will project our schema onto this shape.

Mismatch produces `PolicyError`, distinguishable from `VerificationError` thrown for cryptographic failure. This is the linchpin of G2 codex tightening: "signature without identity policy is theater."

### 6. Audit-warn vs fail-closed in offline strict mode

Decision (codex G2 endorsed):
- `mcpVerificationMode='strict'` + offline + bundle attached → **allow** (verify runs offline, succeeds).
- `mcpVerificationMode='strict'` + offline + no bundle → **block** (no signature to verify).
- `mcpVerificationMode='warn'` + offline + no bundle → **audit-warn-allow**.
- `mcpVerificationMode='off'` → skip verify (record stays `verification_status='unverified'`).

Air-gapped enterprise users without a network can install signed plugins as long as the `*.sigstore` bundle is delivered alongside the manifest (e.g., via internal artifact mirror). `tuf.sigstore.dev` is **never** contacted at runtime.

### 7. TUF root refresh policy

- TUF root checked in at `src/main/mcp/sigstoreRoot.json` (US-202).
- Refresh script: `scripts/refresh-sigstore-root.cjs` (US-202) — invoked manually before release; result ships via electron-updater.
- Release checklist gates `now - lastTufRefresh > 6mo` (AC-6.7) — printed warning at `npm run release-check`.
- Stale root scenario (>6 mo, miss release): Verifier rejects (cert chain lookup uses outdated trust). User-visible toast "MCP plugin verification needs an app update". Roll-back: env `DREAMPIA_DISABLE_SIGSTORE=1` for emergency only.

## Risks / known limits

- The Sigstore root is a moving target (~yearly rotation). If a release misses the rotation window, all installs fail until app updates. Mitigation: 6-month warning gate + electron-updater channel + roll-back env.
- `gh attestation`-produced bundles are required (not bare `.sig` files). Plugin author docs (US-105 / US-700 finalize) must say so.
- `@sigstore/verify` does not solve revocation. Revocation is handled separately by `signedRevocationFeed` (US-203, G3 codex tightening).

## Two-path recovery (would have applied if NO-GO)

If the spike had failed (bundle >5 MB OR Electron incompat OR no offline support OR no identity policy API):

1. **Lighter primitive path**: drop `@sigstore/verify`, ship Ed25519 static-key verify (developer self-signed + bundled trust root) + TOFU on first install. Effort ~2d. Acceptable if v2.3.0 timeline pressure forces.
2. **Re-scope path**: pull v2.3.0 marketplace down to "Marketplace + Local browse UI" tier — no signature verify, all installs unsigned with prominent banner. Effort 0d (revert Phase 2.1+ work). Defers signed marketplace to v2.4.0.

Neither path triggered.

## Decision

**GO** — Phase 2.2 (US-201) `manifestVerify` proceeds against `@sigstore/verify@^3.1.0`. Identity policy enforced via `certificateIdentities[]`. Offline strict-mode supported via bundled trust material + inclusion proof in `*.sigstore` bundle. Bundle size ~848 KB, well within budget.

US-200 closes; US-201/202/203 unblocked.
